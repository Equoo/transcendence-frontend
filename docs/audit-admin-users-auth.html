Côté back / Swagger

PointDétail
GET /auth/logout, GET /auth/refreshDes GET qui modifient l'état : un lien ou une image tierce peut déconnecter l'utilisateur. À passer en POST.
Erreurs non documentées/roles*, /users/{id}, /me/password, /auth/{id}/password ne déclarent que « 200 » : pas de 400/401/403/404, pas de schéma de réponse pour GET /roles. Le front est obligé de deviner. Aucun securitySchemes non plus.
Permissions à vérifierLes gardes du front sont cosmétiques. Vérifier que le back refuse : supprimer/déconnecter/changer le mot de passe de soi-même ou d'un admin supérieur, se donner des permissions via PATCH /roles/{id}/permission, supprimer le dernier admin.
Endpoints non utilisésGET /me/tokens (liste des sessions) et GET /users/{id}. Idée de feature : « Mes sessions actives » dans le profil.
channelsAckMsgDéclaré nullable dans GetMeResponse et absent de ListUsersResponse. Le front doit gérer les deux cas (voir constat « normalizeUser »).

Plan d'action proposé

Dans cet ordre, c'est environ une demi-journée pour les 4 premiers points.

  1. Un helper d'erreur unique (assertOk(res)) et des actions qui renvoient { ok, error } au lieu de lancer : règle les constats 1, 2, 3 et la duplication APIError d'un coup.
  2. ChangeModal : champs type="password" et minLength séparé pour le mot de passe actuel.
  3. Petits bugs rapides : normalizeUser null-safe, date d'invitation en ISO, condition de AdminSidebar, caches initiaux undefined.
  4. Garde-fous admin : désactiver les actions sur soi-même, sélecteur de rôle par id, checkbox désactivée pendant l'envoi.
  5. Ensuite seulement : cohérence (nommage, format Prettier) et accessibilité.
